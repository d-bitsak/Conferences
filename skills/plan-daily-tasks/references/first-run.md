# Мастер первого запуска


Содержание: вход и возобновление; способ работы; источники; предпочтения; пробный список; личное состояние; выбранные дополнения; карточка.

## Вход и правила диалога


Запускать по «Настрой планирование дня», «Продолжи настройку» и запросу изменить источники/режим. Для обычного «Покажи мои задачи» использовать существующую настройку и не навязывать полный мастер; если её нет, выяснить лишь необходимую область/источник/зону.

Прочитать bootstrap, config, state и setup manifest по setup.md, если они подключены. Возобновлять незавершённый или затронутый изменением шаг; не сбрасывать разрешения, исходные карты и неизвестные исходы. Для изменений готовить кандидат, сохраняя действующую конфигурацию до проверки.

Самостоятельно проверять инструменты, профили и технические детали. Задавать обычно один вопрос за ход, максимум три коротких вопроса одним блоком. Не спрашивать то, что уже известно; не просить пользователя искать ID, API-поля или объяснять хранение JSON. Не просить токены и пароли.

## Шаг 1. Определить желаемый способ


Использовать названное пожелание. Только при неясности предложить планирование по команде или дополнительно автоматический утренний список, если такая возможность реально доступна.

Начинать с чтения и focus_only. Календарь и перенос карточек подключать по выбранному сценарию. Если пользователю нужен только список/фокус, не требовать write-доступа и расписания.

Зафиксировать желание отдельно от разрешения и фактического включения. Установка и общее «настрой» не означают разрешение менять статусы, календарь или выполнять задачи.

## Шаг 2. Обнаружить нужные источники


Прочитать актуальные схемы инструментов и минимальные метаданные выбранных подключений. Проверить текущую личность в каждой системе, разрешённые проекты/области, чтение, пагинацию, реальные статусы и ссылки.

Не читать весь командный backlog и чужие карточки ради демонстрации. При нескольких аккаунтах/областях предложить проверенные названия и уточнить выбор. Не требовать от пользователя технических ID.

Недельный контекст читать только для соответствующего планировщика. Для посредника запросить реальные вызовы и полноту в его собственном источнике, не посылать ему данные остальных.

Для каждого шага сохранять not_checked, passed, blocked или not_required, evidence_refs и причину. Один недоступный источник не блокирует доступные; частичную проверку не называть полной.

## Шаг 3. Получить оставшиеся предпочтения


Уточнить только отсутствующее:

- какие личные источники и области включить;
- в какой IANA-зоне планировать;
- нужны ли встречи/подготовка и какие календари использовать.

Вопрос о переносе карточек задавать при соответствующем пожелании; иначе объяснить базовое правило «Выбор сохраняется как фокус, статусы не меняются». Если перенос нужен, согласовать человеческий смысл отдельно для каждого источника и самому проверить реальную операцию.

Время/канал утреннего списка спрашивать только при выборе автоматики. Не назначать время и фиксированный UTC-offset автоматически.

## Шаг 4. Показать первый полезный результат


Получить свежий список по workflow.md. Для небольшой пробы можно показать явно обозначенную часть разрешённой выборки; не выдавать её за все задачи и не подменять реальные карточки выдуманными.

Показать проверенные ссылки, фактические статусы и сквозные номера, сохранить точную карту. Предложить выбрать фокус. Пробный выбор обработать в focus_only; включение постоянного переноса не проверять скрытым изменением живых карточек.

После ответа отдельно показать подтверждённый фокус и доступный календарь. При нуле доступных кандидатов не просить выбрать отсутствующие номера; отличать проверенный ноль от недоступности источников.

## Шаг 5. Сохранить состояние и независимую ссылку


1. Самостоятельно подобрать доступное подходящее личное хранилище. Уточнять выбор лишь при неоднозначной принадлежности, видимости или существенно разных назначениях. Не спрашивать «Где хранить JSON?».
2. В рамках разрешённого назначения сохранить рабочие config, state и setup manifest по комплектным примерам. Не заменять существующие карты и фокус пустым шаблоном, не переносить рабочие данные в скилл.
3. Для карт/снимков применять схему state-and-recovery.md. Если устойчивого места нет, оставить точное сообщение с датой, ID/ссылками как карту и явно указать предел новой сессии; базовый список и фокус остаются доступны.
4. Создать bootstrap manifest и проверить владельца/все ссылки. Зарегистрировать bootstrap_ref в постоянном контексте своего агента, сохранив остальные инструкции; для расписания добавить его в prompt.
5. Перечитать сохранённый контекст/prompt и открыть настройки по прямым ссылкам без памяти беседы. Отдельный запуск чтения использовать, если он доступен; иначе не заявлять о реальном испытании нового запуска.
6. Для внешних изменений проверить устойчивое сохранение исходов и успешное резервирование конкретной операции до API-вызова: реальную условную запись либо исключительное владение на всём интервале. Зафиксировать доказательство в state_guard/manifest; один флаг verified не заменяет проверку. Если защиты нет, оставить изменения заблокированными, продолжить focus_only.

## Шаг 6. Включить выбранные дополнения


Для календаря проверить доступ, пагинацию и точные экземпляры выбранного дня. Недоступность не означает отсутствие встреч. Соблюдать focus-and-calendar.md; не изменять события.

Для переноса карточек проверить today_mapping, write-контракт, точную область разрешения и личность. Сначала показать, что именно произойдёт с выбранной карточкой. Получить только недостающее разрешение; уже прямую команду не согласовывать повторно. Сохранить ACTIVE и write_source_ids только для готовых разрешённых источников. Без mapping оставить выбор без изменения, не назначать произвольный срок «сегодня».

Для утреннего списка:

1. Проверить существующие запуски и не создавать дубль.
2. После прямого запроса подготовить реальное расписание, IANA-зону и личный канал. Сохранить bootstrap_ref, область чтения и правила выбора в prompt. Явно указать проверку automation.enabled/разрешения: пока включение не подтверждено, только проверять ссылки без доставки списка.
3. До завершения проверок держать новый запуск выключенным либо в явно ограниченном режиме только чтения без доставки.
4. Включить и перечитать enabled, время, зону, ближайший запуск, prompt и назначение. Проверить ссылки на config/state, затем сохранить фактические automation.enabled=true/active_since и перечитать итоговую конфигурацию. Настроенный запуск не объявлять выполненной утренней доставкой. Для чтения/списка без изменения карточек сохранять REVIEW; ACTIVE не включать ради одного расписания.
5. Каждое утро читать актуальные карточки, создавать новую карту и ждать нового ответа. Не применять вчерашние номера, не выбирать автоматически и не менять статусы по расписанию.

Автоматика не нужна для действий по команде. Включение расписания не скрывает давние незавершённые карточки и не запускает импорт истории фокуса.

## Шаг 7. Выдать карточку и завершить


Сформировать setup-result.md по сохранённым и перечитанным фактам. При частичном результате назвать доступную функцию, конкретную блокировку и один следующий шаг.

Не показывать большую карточку после каждого обычного вопроса. Для «Продолжи настройку» читать manifest и проверять лишь незавершённое/изменённое. Не повторять интервью, не выбирать задачи за владельца и не повторять внешнюю операцию с unknown.

Статусы manifest: not_started, in_progress, ready_on_demand, active, partial, blocked. requested_features: candidates, focus, calendar, today_updates, morning_schedule. passed требует доказательства; not_required — объяснения, почему проверка не нужна сценарию.

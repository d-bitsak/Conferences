# Карточка результата настройки

## Когда показывать

Выдавать при завершении мастера, технической блокировке, значимом изменении настройки и команде «покажи настройки». Во время обычного сбора предпочтений достаточно короткого вопроса и подтверждения уже известных параметров: не разворачивать карточку после каждого уточнения. Не добавлять её к каждому протоколу встречи.

Генерировать по рабочей конфигурации, setup manifest и перечитанным настройкам запусков. Намерение, prepared и заполненный пример не доказывают сохранение, включение или успешную проверку.

## Общий статус

| Статус | Условие |
| --- | --- |
| Готово к разбору по команде | Пользователь выбрал этот способ, доступен разбор выбранного источника; показывать только реально доступный вариант |
| Готово к автоматической обработке | Все запрошенные направления разрешены и проверены, ACTIVE сохранён, независимые ссылки доступны обоим запускам, оба запуска включены и перечитаны |
| Частично готово | Доступна часть желаемых функций, остальные блокированы/не проверены; обязательно назвать обе части |
| Настройка приостановлена | Запрошенный способ пока недоступен и подходящий источник/вариант использования не подтверждён |

Если хотели автоматику, а получился только ручной разбор, использовать «Частично готово», не «Всё настроено». Не менять желание пользователя на запасной вариант без его решения. Не называть личный разбор готовым при неподключённом источнике: можно указать «Доступен разбор предоставленного файла», если это действительно поддерживается.

## Шаблон карточки

Показывать короткую вводную и компактную таблицу. Удалять необязательные строки и незапрошенные направления; не выводить заполнители или пустые блоки. Не включать токены, пароли, служебные ID, CAS/lease, внутренние JSON и журнал событий.

```markdown
**Анализ встреч — {общий статус}**

| Параметр | Результат |
| --- | --- |
| Как пользоваться | {По команде / автоматически / доступная часть и ограничение} |
| Источник | {Проверенный аккаунт и источник либо предоставленный файл} |
| Какие встречи | {Подтверждённая область; политика старой истории} |
| С какого момента | {Фактическая отсечка с зоной; только для включённого направления} |
| Куда поступает результат | {Проверенные получатели/личное место/отправитель для каждого запрошенного направления} |
| Состав материалов | {Итоги, фактическая ссылка, TXT и разрешённые дополнения} |
| Задачи | {В итогах / проверенный трекер и собственный исполнитель; если это обсуждалось} |
| Новые записи | {Проверенный включённый способ запуска либо честный статус} |
| Ожидание транскрипта | {Реальная частота и предел проверок либо отсутствие будущего запуска} |
| Настройки | {Сохранены и проверены для следующих запусков / только в этой беседе / что осталось проверить} |

**Проверено:** {2–4 факта с реальным результатом; различать подготовку и выполненную проверку}.

**Требует действия:** {Одна конкретная проблема, что она блокирует и ближайший шаг; только при наличии}.

**Первая команда:** «{Короткий применимый пример использования}».
```

Если несколько направлений имеют разное состояние, заменить строку «Куда поступает результат» небольшой таблицей «Действие / Статус / Назначение или причина». Статусы: «Работает по команде», «Включено автоматически», «Разрешено, настройка не завершена», «Нужны данные», «Нужен доступ», «Не запрашивалось». Последний статус показывать лишь когда он помогает снять конкретную неоднозначность.

Для автообработки без новой поступившей записи писать «Запуски включены и перечитаны; первая автоматическая обработка ещё не подтверждена». Не заявлять успешную отправку, создание задачи или доставку тестового письма по факту настройки.

Если пробная встреча до active_since, явно указать, что включение новых записей не отправило её. Если пользователь отдельно попросил отправить пробу, сохранять её отдельный исход.

Для неизвестных фактов писать «Не проверено» и объяснять последствия. Для отсутствующей активации писать «Автоматическая обработка пока не включена», а дату начала не заполнять.

## Данные для продолжения

В личном setup manifest хранить requested_usage, requested_channels, bindings, checkpoints, evidence_refs и blockers. В checkpoints различать not_checked, passed, blocked и not_required; для passed требовать реальное доказательство, для not_required — объяснение, почему проверка не нужна выбранному сценарию.

Использовать requested_usage=on_demand или automatic. Статус manifest: not_started до начала, in_progress во время обычного диалога, ready_on_demand для готового разбора по команде, active для полностью проверенной автоматики, partial для доступной части запроса с блокировками, blocked когда запрошенный способ и применимый источник пока недоступны. Общий статус карточки получать из этих фактов; не переносить его в операционные состояния встреч.

Не включать эти доказательства целиком в карточку. Ссылку на личные настройки можно показать по запросу владельца; не раскрывать его приватные назначения в общую папку или распространяемый скилл.

После «продолжи настройку» прочитать этот manifest через независимую ссылку, проверить актуальность зависящих от изменений шагов и выдать обновлённую карточку. Для возобновления обработки встреч использовать операционный журнал state, а не статус мастера.

# Журнал, идемпотентность и восстановление

## Устойчивое состояние

Использовать отдельный личный журнал владельца; assets/state.example.json содержит только пустой пример. Не считать память чата журналом и не включать рабочий журнал в передаваемый скилл.

Находить журнал через проверенный bootstrap_ref и связанные config/state по first-run.md. Прогресс мастера хранить отдельно в setup manifest: его checkpoints не являются доказательством отправки или заменой операционных состояний встречи.

Хранить account, occurrence ID, время/зону, хеш и метрики источника, проект и основание классификации, event/calendar IDs, снимок адресатов и отдельное состояние каждого направления/карточки. Добавлять attempt ID, lease, источник разрешения, provider/run/message/task/file IDs и результаты проверок. Не хранить пароли, токены, временные signed URL, полные запросы с секретами и чужие материалы.

Разделять устойчивую идентичность встречи и версию источника. Для подтверждённого обновления файла сохранять прежний meeting key, прежние результаты и новый хеш версии. Не превращать обновление текста в новый экземпляр ради обхода дедупликации.

## Состояния

| Состояние | Значение и следующий шаг |
| --- | --- |
| discovered | Экземпляр найден; проверить источник и область |
| waiting_assets | Источник готовится; чтение только по next_check_at |
| prepared | Результат подготовлен; внешнее действие ещё не принято |
| reserved | Попытка условно закреплена за исполнителем; сохранить attempt и lease |
| accepted | Провайдер принял действие; повторное создание/отправка запрещены |
| verified | Требуемый конечный результат проверен; письмо этим статусом не объявлять доставленным |
| unknown | Исход неизвестен; сначала выяснить прежнюю попытку |
| blocked | Не хватает права, данных или решения; указать конкретную причину |
| failed | Подтверждённая ошибка; проверить отсутствие/частичность побочного эффекта |
| duplicate | Уже существует точный результат; сохранить ссылку/ID |
| no_tasks | Собственных новых действий нет; создание карточек не требуется |

Хранить acceptance и verification отдельно: accepted с незавершённой проверкой остаётся открытым для чтения результата, но закрытым для повторного создания. Отдельно сохранять provider status и время последней проверки. Состояние встречи в целом выводить из направлений; успех одной ветки не закрывает остальные.

## Резервирование

1. Прочитать полный актуальный журнал и реальную версию. Не заменять его усечённым превью.
2. Выбрать стабильный ключ: account + occurrence + channel + destination; для карточки добавить устойчивый ключ действия/источника.
3. Условно сохранить reserved с actual expected version, attempt ID и ограниченным lease. Эквивалентный подтверждённый эксклюзивный lock допустим для действительно последовательного локального хранилища.
4. При конфликте перечитать и пересчитать. Не трогать живую чужую reservation и не выполнять действие по старому снимку.
5. Если резервирование не подтверждено, не делать внешний вызов.
6. После ответа немедленно сохранить подтверждённые ID и состояние. При конфликте записи результата сохранить известный provider ID и восстановить запись без повторного внешнего вызова.

Простой JSON-файл без согласованного механизма конкуренции не гарантирует резервирование. При невозможности надёжной записи приостановить внешние действия, продолжить REVIEW и безопасные проверки чтением.

## Неопределённость

Тайм-аут, потеря ответа, незавершённый run или истёкшая reservation не доказывают отсутствие действия. Ставить unknown и проверять отправленные сообщения/результат API/карточки/архив по сохранённым ID и признакам.

Если действие обнаружено, сохранить его и продолжить проверку; не отправлять снова. Только проверенное отсутствие эффекта допускает повтор в разрешённой области, с тем же поддерживаемым ключом и тем же телом. Без проверенной идемпотентности и при неустановимом исходе запросить решение владельца.

Не выдумывать idempotency header и не менять ключ/UUID, чтобы обойти неизвестную или принятую попытку. Если failed мог частично создать задачи/публикации, сначала сверить эти эффекты. Не обещать exactly-once: внешний вызов и сохранение журнала не составляют общей транзакции.

## Ожидание и изменения

Увеличивать интервалы по настроенному waiting, учитывать Retry-After и общий предел. При исчерпании срока оставить blocked и один раз уведомить. Будущий запуск должен быть реально настроен; значение next_check_at само по себе его не создаёт.

Для периодического обнаружения новых записей сохранять подтверждённую позицию обхода и время последнего чтения в discovery журнала. Ограничивать первое чтение разрешённой отсечкой, последующие — сохранённой позицией и безопасным перекрытием с дедупликацией; не использовать пустой cursor как разрешение читать всю историю.

Повторять только безопасные чтения и проверенно не выполненные действия. Новая версия транскрипта, адресатов или скилла не разрешает письмо-исправление, дополнительную рассылку, изменение карточки или исторический импорт. Применять отдельно согласованную политику исправлений.

# Мастер первого запуска

## Вход и возобновление

Запускать для «настрой анализ встреч», «первый запуск», «включи обработку встреч», «продолжи настройку» или явного запроса изменить настройки. Если пользователь уже дал файл/конкретную встречу и хочет только разбор, сразу выполнить его в REVIEW; не навязывать подключение сервисов и мастер автоматики.

Сначала найти рабочие настройки по правилу независимой ссылки ниже. При найденной настройке продолжать с первого незавершённого или затронутого изменением шага. Не обнулять журнал, разрешения, дату начала и работающие направления. Для изменений готовить кандидатную конфигурацию; применять только согласованные изменения после проверки, сохраняя остальные поля и историю.

Вести личный setup manifest по assets/setup-state.example.json, когда доступно выбранное личное хранилище. До его появления продолжать доступные шаги в беседе, но не обещать их сохранение между сессиями. Разделять запрос пользователя, проверенные факты, сохранённые настройки и фактическое включение.

## Правила диалога

- Начать с одной фразы о ближайшем результате: «Проверю доступные подключения, затем разберём одну встречу и настроим выбранные действия».
- Сначала самостоятельно проверить доступные инструменты и уже настроенные профили; не просить пользователя перечислять ID, API-поля или возможности хранилища.
- Задавать только недостающие пользовательские решения: обычно один вопрос за ход, максимум три коротких вопроса одним блоком. Не спрашивать то, что уже сказано или однозначно подтверждено профилем.
- Не объяснять пользователю CAS, lease, JSON-схемы и внутренние ключи. Переводить препятствие в последствие: «Хранилище не защищает от одновременной отправки одного письма».
- Не просить пароли, токены и ключи в чате. При отсутствии подключения назвать нужный сервис и доступное действие подключения; не выдумывать интерфейс или кнопку Dots.
- Не заявлять о выполненной проверке, записи или запуске по одному наличию инструмента, устному заверению либо заполненному примеру.

## Шаг 1. Выбрать способ использования

Использовать уже названное пожелание. Только при неопределённости предложить:
1. Разбирать встречи по команде и показывать результат в чате.
2. Автоматически готовить личные итоги, если среда поддерживает такой запуск и доставку владельцу.
3. Автоматически отправлять материалы приглашённым.

Подключать задачи, архив и API только по запросу, без обязательной анкеты по всем пяти направлениям. Отдельно фиксировать желаемый способ работы и его техническую доступность: запрос автоматики не равен её включению.

Разрешение «настрой» даёт основание для необходимых проверок и личного сохранения настроек. Для постоянной рассылки/карточек/архива нужна прямая команда с конкретной областью. Если такая команда уже получена, не спрашивать её повторно.

## Шаг 2. Самостоятельно проверить необходимые возможности

Прочитать актуальные схемы доступных инструментов; выполнить минимальные разрешённые чтения и проверить только зависимости выбранного сценария. Проверять профили и выбранную встречу; не сканировать чужую переписку, всю историю или посторонние папки.

| Сценарий | Необходимые проверки |
| --- | --- |
| Разбор файла в чате | Чтение всего файла; сохранение спикеров/таймкодов при наличии |
| Разбор подключённой встречи по команде | Собственный профиль, точный экземпляр, полный транскрипт |
| Письмо приглашённым | Предыдущее плюс соответствующее приглашение, авторизованный sender и поддержка одного TXT-вложения |
| Личные итоги по расписанию | Источник, подтверждённый способ запуска и доставки именно владельцу |
| Создание задач | Личность владельца/спикера, целевой профиль, чтение дублей и создание с проверкой результата |
| Архив или API | Реальный контракт/назначение, доступ и проверка конечного результата |
| Любые внешние действия | Устойчивый журнал, условное резервирование и действующее разрешение |
| Автоматическая работа | Предыдущее плюс поиск новых записей, повтор открытой очереди и постоянные ссылки в контексте запусков |

Для каждой зависимости фиксировать not_checked, passed, blocked либо not_required с кратким основанием и evidence_refs. Непроверенную возможность не считать доступной. Для личной доставки без сообщения в чат допустим подтверждённый штатный канал результатов автоматизации; не предполагать его наличие или адресацию.

## Шаг 3. Получить недостающие предпочтения

Собирать небольшими порциями:
- область встреч: все новые собственные или указанные проекты/календари;
- получатели/место результата и отправитель, если после проверки остаётся выбор;
- IANA-зону для дат и сроков, если она ещё не подтверждена.

По умолчанию предложить начало с момента включения и исключение старой истории; не заставлять выбирать дату без необходимости. Не выводить зону владельца из зоны сервера или UTC в примере.

Для письма явно объяснить выбранное правило: «Все приглашённые из конкретного события Calendar, включая отсутствовавших». Если пользователь требует только присутствовавших, проверить доступность надёжного сопоставления их адресов и согласовать это правило; не подменять его списком гостей молча.

При одном проверенном аккаунте предложить его как отправителя. При нескольких подходящих аккаунтах спросить, какой использовать. Для личных задач уточнять личность спикера только когда она нужна и не подтверждена.

Для простого сценария «все новые собственные встречи → письмо» согласовать эту область и задать default_routes=["email"]. Для проектных различий заполнять projects и их routes. Одного email.enabled=true недостаточно.

## Шаг 4. Дать первый результат

Найти одну указанную пользователем встречу; при отсутствии выбора предложить один проверенный подходящий экземпляр в разрешённой области. Не рассылать пробную встречу и не создавать её карточки по факту подготовки примера.

Отдельно выбранная владельцем пробная встреча может быть до будущей отсечки активации. Её разбор не включает исторический импорт и не разрешает автоматическую отправку после включения.

Самостоятельно получить и проверить полный транскрипт. Показать короткие итоги, предполагаемых адресатов/назначения и собственные задачи, если они запрошены. Создать полный TXT в разрешённом личном рабочем месте, когда это поддерживается. Если файл только запланирован, так и написать; отсутствие пути создания TXT блокирует зависящие от него направления, но не разбор в чате.

Отдельно указать пробелы, влияющие на результат. Не спрашивать повторное одобрение всего примера, если пользователь уже прямо разрешил действие и существенных неоднозначностей нет. Использовать пример для проверки материалов, а не как фиктивное доказательство доставки.

При недоступном источнике показать конкретную проблему и предложить разбор предоставленного транскрипта. Для задачи первого разбора не делать исправность автоматики предварительным условием.

## Шаг 5. Сохранить личные настройки и независимую ссылку

Выполнить самостоятельно, не задавая вопрос «Где хранить JSON?»:
1. Найти подходящее доступное личное хранилище по текущим инструментам. Проверить владельца, доступ и существующие настройки. Предложить пользователю понятное место; спрашивать выбор только при неоднозначной принадлежности/видимости или нескольких существенно разных назначениях.
2. Создать рабочие config, state и setup manifest в этом месте. Не изменять распространяемые assets и не заменять существующий журнал пустым примером. Сохранять полный актуальный объект с проверкой версии там, где она поддерживается.
3. Для внешних действий проверить реальный контракт условной записи/исключительного владения. При необходимости использовать собственную пустую пробную запись: успешная запись по текущей версии, отклонение устаревшей версии, чтение результата. При проверенном альтернативном lock зафиксировать его область. Не портить действующий журнал тестом.
4. Создать личный bootstrap manifest по assets/bootstrap.example.json с owner_ref, config_ref, state_ref и setup_ref. Перечитать все ссылки и проверить их принадлежность тому же владельцу.
5. Зарегистрировать bootstrap_ref в доступном постоянном контексте именно этого агента, сохранив остальные инструкции. Для автоматических запусков явно включить его в каждый prompt. Запись только внутри config/state не решает обнаружение.
6. Перечитать сохранённый постоянный контекст/prompt и затем открыть bootstrap, config и state по этим ссылкам без опоры на память беседы. Если доступен отдельный запуск проверки чтения, использовать его; иначе честно зафиксировать проверку ссылок и prompt, не заявляя о реальном новом запуске.

Если подходящего журнала нет, сохранить допустимые личные настройки как REVIEW с конкретной блокировкой внешних действий. Не считать обычную перезапись JSON или обещание запускать вручную доказательством защиты от конкуренции. Продолжить доступный разбор по команде. Если постоянный контекст недоступен, не обещать нахождение настроек после новой сессии.

## Правило независимой ссылки

В каждом запуске искать в порядке:
1. Явный bootstrap_ref в текущем запросе/сохранённом prompt запуска.
2. Зарегистрированный bootstrap_ref в постоянном контексте этого агента и владельца.
3. Явно переданную владельцем ссылку на рабочую конфигурацию с проверкой профиля и связанных журналов.

Не искать журнал по памяти прежнего чата и не сканировать все файлы ради совпадения имени. Если ссылки отсутствуют или противоречат владельцу, считать конфигурацию неподключённой и уточнить ровно недостающую ссылку/привязку. При возврате к настройке восстановить setup manifest, проверить актуальность evidence и продолжить с незавершённого шага. Не повторять неизменные вопросы и успешные операции.

## Шаг 6. Подготовить включение

Составить конкретную настройку выбранных направлений: источник, область, адресаты/место, состав материалов, маршруты и отсечка. Проверить dependencies каждой ветки и получить только ещё отсутствующее разрешение.

Если разрешения нет, после подготовки примера и проверок задать один конкретный вопрос: «Включить обработку новых собственных встреч с момента запуска и отправку {состав материалов} {проверенным адресатам/по подтверждённому правилу}?». Не спрашивать повторно при уже действующей прямой команде. Пароль записи включать только при отдельном разрешении и реальной необходимости; не расширять состав молча.

Для автоматики:
1. Проверить существующие запуски и их область, чтобы не создать дубль.
2. Выбрать реально поддерживаемый способ обнаружения новых записей: событие источника/почты либо согласованная периодическая проверка с отсечкой и сохранённой позицией обхода. Не выдумывать webhook. В обоих вариантах проверять источник и account.
3. Настроить повтор только открытой очереди с next_check_at, unknown и незавершённой проверкой accepted. Не повторять их внешнее создание. Согласовать реальные интервалы waiting с частотой доступного запуска: не обещать проверку через 5 минут при запуске раз в 30 минут.
4. Сохранить в обоих prompt bootstrap_ref, область, источник разрешения, запрет backfill, правило независимых направлений и восстановление. Перечитать ID, enabled, trigger/schedule и prompt.
5. До завершения проверок держать новые запуски выключенными, если это поддерживается. Иначе использовать явно сохранённую кандидатную конфигурацию REVIEW: новые запуски могут только читать/готовить, пока не подтверждена активация. Не изменять работающие чужие/неоднозначные запуски.
6. После проверки обоих запусков включить их, пока кандидатная конфигурация остаётся REVIEW, и перечитать их enabled/prompt. Только после подтверждения обоих запусков и разрешения сохранить ACTIVE для готовых направлений, фактические active_since и automation.enabled, затем перечитать конфигурацию и привязки. Для донастройки работающего процесса держать новые направления выключенными до этой точки и не отключать прежние. Обрабатывать только записи в подтверждённой области и после отсечки. При частичном сбое включения сохранить точный результат и не объявлять автоматический режим готовым.

Не сбрасывать существующий active_since при донастройке. Для впервые включаемого направления сохранить отдельную отсечку в его конфигурации; не превращать это в обработку ранее накопленной очереди без команды.

Для действий только по команде не требовать расписаний. Для чистого REVIEW в чате не требовать внешнего хранилища и журнала. Для разовой внешней операции журнал обязателен, а создание постоянных запусков не требуется.

## Шаг 7. Выдать карточку и завершить

Сформировать карточку по references/setup-result.md из перечитанных фактов, а не из желаний пользователя. Обновить setup manifest, сохранив доказательства отдельно от краткой карточки.

При частичном результате назвать доступный способ использования, конкретную заблокированную функцию и одно следующее действие. Не просить повторно разрешение на уже согласованное. Сохранить разрешение и прогресс для продолжения, когда это технически возможно.

Для повторной настройки показать изменённые поля и актуальную карточку; не заставлять проходить весь мастер заново.
